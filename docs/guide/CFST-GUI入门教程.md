# CFST-GUI 教程

绝大多数人测 Cloudflare 优选 IP 都有一个误区：**盲目扫全网段、无脑拉高测速并发，结果跑出来的 IP 要么实际拉不动流，要么满屏报 `1034` 无法访问。**

**CFST-GUI**（项目地址：[https://github.com/axuitomo/CFST-GUI](https://github.com/axuitomo/CFST-GUI)）并非简单的套壳工具，它内置了一套严密的**四级漏斗过滤管线**与 **MICS 智算抽样引擎**。本教程将带你从底层逻辑出发，吃透输入源配置、COLO 地理预筛、Trace 链路探测及真实吞吐测速的全流程。

## 核心架构：CFST-GUI 是如何筛选出“真·优选 IP”的？

在动手点按钮之前，先理解软件的**四阶段漏斗模型**，你就能明白每一个参数存在的意义：

| 阶段 | 核心工作 |
| --- | --- |
| IP 池 | 清洗注释/展开 CIDR/域名解析/去重 + MICS 抽样 |
| TCP 测延迟 | 剔除高延迟与高丢包节点，按 RTT 升序截取优质池 |
| 追踪探测 | 请求 `/cdn-cgi/trace`，校验 HTTP 状态码、真实 COLO 机场码及 1034 拦截 |
| 文件测速 | 对通过追踪阶段的节点执行下载测试。测出真实可用带宽 |

### 使用前务必先设置导出位置

开始前先在 **「系统配置」→「通用设置」** 设置导出目录，测速结果默认写入该目录的 `result.csv`；其余细节见 [快速上手](./quick-start.md)。

## 第一步：前置基建（COLO 地理词典）

很多教程教你上来就填 IP 测速，但如果你不想把时间浪费在绕地球半圈的南美或欧洲节点上，第一步必须先激活本地 **COLO 词典**。

1. 打开左侧边栏 **「系统配置」→「通用设置」→「COLO 词典」**。
2. 依次点击 **「更新词典」**（拉取 Cloudflare 官方 `GEOFEED` 与城市映射表）→ **「处理词典」**（生成本地 IPv4 / IPv6 索引库）。
   - 注：仅点“更新”不会生效，必须两步全点，直到状态卡片出现具体的 IPv4/IPv6 行数与最新时间戳。
   - 从旧版升级后建议重新「更新+处理」一次

| 状态项      | 含义                                        |
| ----------- | ------------------------------------------- |
| GEOFEED     | 原始 IP 段表行数                            |
| 综合        | 合并后的 COLO 映射（含 IPv4+IPv6）          |
| IPv4 / IPv6 | 按地址族拆分后的行数                        |
| 未覆盖      | 暂时无 COLO 的 GEOFEED 行（不代表测速失败） |
| 更新时间    | 最近一次处理时间                            |

## 第二步：构建高含金量输入源

进入侧边栏 **「输入源」**。CFST-GUI 引入了「输入组」概念，你可以为不同用途（如：自建反代专属组、大宽带通用组、移动/电信专线组）建立独立方案。

### 1. 添加来源与主流数据源参考

点击右上角 **「＋」**，支持三种导入方式：

- **本地文件**：适合导入外部高频更新的优选名单（如 Telegram 优选频道发布的每日 `ip.csv` / `ip.txt` 成品库）。

- **URL 列表**：填入远程订阅链接（抓取时自动跟随系统代理），每次启动任务都会实时拉取最新列表。

- **手动输入**：支持直接粘贴混合格式，引擎会自动跳过空行与 `#` 注释：

  ```Plaintext
  1.1.1.1
  104.16.0.0/24          # CIDR 段自动展开
  1.1.1.1:2053           # 指定非标端口
  [2606:4700::1]:443     # IPv6 标准格式
  ```

### 常见卡点速查

| 现象              | 原因                      | 处理                                            |
| ----------------- | ------------------------- | ----------------------------------------------- |
| 预览 0 条         | URL 404 / 文件空 / 格式错 | 浏览器验证 URL；检查每行是否为合法 IP/CIDR/域名 |
| URL 读取失败      | 需代理 / 证书 / 限流      | 跟随系统代理；先在浏览器确认可访问              |
| 加节点筛选后 0 条 | 词典未处理或代码写错      | 先更新并处理 COLO 词典；或暂时清空筛选          |
| 启动按钮灰色      | 无启用来源 / 已有任务     | 打开开关；先完成或终止当前任务                  |

### 2. 组级高阶策略（展开顶部「输入组设置」）

- **输入组 IP 模式**：
  - **逐个检查**：适合几百到几千条的精选 IP 列表，全量遍历不遗漏。
  - **随机抽查（MICS 抽样）**：当你导入了动辄几十万 IP 的全网 CIDR 段时，务必开启此项，引擎会通过多臂老虎机/分层抽样快速锁定优质子网，避免耗时过长。
- **节点筛选（地理预筛）**：填入目标机场三字码或国家码（如 `HKG,NRT,SIN,SJC`），配合白名单模式，即可在发起任何网络发包前，利用第一步生成的 COLO 词典直接剔除无关地区节点。

## 第三步：核心探测策略与「Error 1034」深度破局

进入 **「系统配置」→「网络与任务」→「探测策略」**，这里决定了你筛选出来的 IP 到底能不能用。

### 1. 必懂硬核原理：为什么测出来的 IP 会报 1034？

很多用户在测速结果里看到一堆状态正常、速度飞快的 IP，填进客户端却直接报错 **Error 1034 (Edge IP Restricted)**。这背后的底层机制如下：

Cloudflare 官方将错误 1034 定义为 **Edge IP Restricted**，即边缘 IP 受到限制。它与 Cloudflare 的边缘 IP 校验机制有关，可能出现在受限 IP 空间、SaaS 提供方 IP 限制或地址映射配置不匹配等场景。

部分用户可能在特定运营商出口、路由路径或目标域名配置下，更容易观察到某些地区节点返回 1034；这属于具体网络环境中的经验现象，不能推导为 1034 的通用成因，也不能据此认定所有 NRT 节点都存在问题。

还要注意：**HTTP 状态码与错误页面中的“1034”不是同一个概念。** 状态码筛选检查的是 HTTP 响应状态；1034 是 Cloudflare 错误编号。排查时应结合结果备注、追踪响应和实际业务域名进行判断，不要把“状态码 200”直接理解为业务请求一定没有问题。

官方说明：[Cloudflare Error 1034 - Edge IP Restricted](https://developers.cloudflare.com/support/troubleshooting/http-status-codes/cloudflare-1xxx-errors/error-1034/)。

**为什么不同追踪域名可能得到不同结果？**

1. **风控机制差异**：Cloudflare 对原生接入域（CF Zone）与 Cloudflare for SaaS（自定义主机名/回退源）采用两套截然不同的边缘校验策略。原生 CF 域审查极严，大量公共 Anycast IP 被禁止直接绑定转发；而 **SaaS 域名的 IP 宽容度极高，极少触发 1034 拦截**。
2. **默认探针的盲区**：软件默认派生出的追踪地址是官方的 `https://speed.cloudflare.com/cdn-cgi/trace`。由于它属于官方 Zone，测试时不会触发业务侧的 1034 策略，可能导致“假阳性”通过；多数 IP 对 `speed.cloudflare.com` 的 trace 不被拦截，而对 `cloudflare.com` 反而可能被拦截。
3. **运营商路由特征**：国内**中国电信**用户尤为常见——当电信骨干网路由将流量牵引至日本东京（NRT）节点时，极易触发 Cloudflare 对 NRT 边缘节点的 1034 严格拦截。

**破局配置方法：**

- **场景 A（用于普通 CF 域名/Workers）**：在 **「第二阶段 · 追踪与地区码」→「追踪 URL」** 中，填入你**自己真实业务域名**的追踪地址（例如 `https://你的域名/cdn-cgi/trace`）。这样探测阶段就会模拟真实访问，提前把 1034 拦截的废 IP 淘汰掉！
- **场景 B（用于 SaaS 优选域名）**：填入你的 **SaaS 域名**追踪地址（`https://你的saas域名/cdn-cgi/trace`），你会发现第二阶段放行通过的可用 IP 数量通常多于场景 A。
- **避坑提醒**：`https://.../cdn-cgi/trace` **只能填在「追踪 URL」里**，千万不要误填进下方的「文件测速 URL」！

### 2. 三大阶段黄金参数推荐表

| **阶段** | **核心参数** | **推荐值** | **调优逻辑与避坑指南** |
| --- | --- | --- | --- |
| **第一阶段** TCP 筛选 | **测速端口 / 策略** | `443` / 固定测速端口 | 若导入了带非标端口的名单（如 `:2053`），切换为「输入源端口优先」。**通常来说都是443端口** |
| | **TCP 并发线程** | 桌面 `200` / 手机 `64` | 光猫或家用硬路由性能较弱时，线程过高会导致 NAT 表爆满、大面积假超时 |
| | **TCP 丢包率上限** | `15%` | 晚高峰跨境丢包严重时，可临时放宽至 25% 。**其实4次发包15%相当于0%** |
| **第二阶段** 追踪探针 | **输入源 COLO 筛选时机** | 预检时筛/追踪阶段再筛 | 靠本地词典零发包预筛；若追求 100% 精准物理机房，可改为「追踪阶段再筛」。 |
| | **追踪有效状态码** | `200` | 严格校验正常响应，过滤边缘拦截页。 |
| | **追踪 URL（可选）** | 留空 或 `https://自用域名/cdn-cgi/trace` | 解决 1034 误判的核心开关（见上文原理）。 |
| **第三阶段** 文件测速 | **文件测速 URL** | 保持默认 | 默认走官方大文件流，也可以用自建测速URL。 |
| | **并发测速 IP 数** | **`1-5`** | **极其重要！** 设大于 1 会导致多个 IP 抢占你本地的总下载带宽，测出的单 IP 速度严重偏低且失真。 |
| | **最低下载速度** | 按需（如 `15` MB/s） | 首次跑建议设 `0` 摸底；摸清带宽上限后设门槛，不达标的 IP 会提前掐断，大幅节省时间。 |
| | **达到成功 IP 数后停止** | 按需（如 `5` 或 `10`） | 凑够指定数量的达标高速 IP 后自动收工，无需跑完整个大池子。**提前跑完节省时间** |

## 第四步：启动任务与结果解读

1. 回到 **「任务看板」**，确认当前输入组与端口策略无误，点击 **「启动任务」**。
2. 任务运行中可实时观察各阶段漏斗转化率；如需临时用网，支持随时**暂停 / 继续**，或点击**终止**（已测出的有效结果会自动保留，不会丢失）。
3. 测速完成后，进入 **「当前结果」** 页：
   - 右上角可按 **IPv4 / IPv6** 过滤，并按 **平均速率** 或 **追踪延迟** 排序。
   - 重点关注「阶段状态」旁的 **COLO 机场码**（如 `HKG` 香港、`NRT` 东京、`SJC` 圣何塞）以及备注标签（若保留了 `403` / `1034` 节点会在此明确标出）。
   - 完整的测速报表会自动导出为 `result.csv` 存放在你设定的导出目录中，方便直接导入其他代理工具或脚本自动化调用。

| 现象 | 先查 | 处理 |
| --- | --- | --- |
| 启动按钮灰色 | 有无启用来源 | 添加并打开开关 |
| IP池 0 条 | 预览是否报错 | 修正 URL/路径/格式 |
| 加地区筛选后空 | 白名单与词典匹配 | 先清空筛选跑一次；更新并处理词典 |
| 文件测速全失败 | URL 返回 HTML 或被拦 | 换回默认 Cloudflare 地址；确认返回文件流 |
| 速度明显偏低 | 并发/代理/链路 | 并发测速 IP 数设回 1；测速阶段直连，不走代理 |
| 出现 403/1034 | 节点被边缘限制 | 换自己站点的追踪与测速地址，或换一批 IP |

## 高频排障速查表

- **TCP 阶段全军覆没（0 通过）**：检查本地是否开启了全局代理软件的 TUN 模式或者端口被拦截（测速阶段必须直连，部分 TUN 模式会劫持并丢弃大量并发 SYN 包）；更换端口或降低 TCP 并发线程。
- **追踪阶段全部超时/失败**：检查是否误把 `https://speed.cloudflare.com/__down` 填进了追踪 URL，或者自建域名的 SSL 证书配置异常。
- **测出来的速度远低于自家宽带上限**：确认「并发测速 IP 数」是否为 `1`；同时检查节点地区——国内三网晚高峰直连美西（`LAX`/`SJC`）单线程跑满 `15–30 MB/s` 属正常物理极限，并非软件限制。
- **Android 端后台测速中断**：进入系统设置或软件内「异常保护」，赋予电池优化白名单并锁定后台任务。
