## 评审框架

### 整体目标权重

| 目标 | 权重 | 说明 |
|------|------|------|
| 性能 | 35% | 日志写入、热数据读写、导出性能、启动速度 |
| 可维护性 | 30% | 路径统一、代码结构、可测试性、可演进性 |
| 跨应用读取 | 15% | Android 日志导出后可被其他应用读取 |
| 数据可靠性 | 10% | 不丢失、崩溃恢复、迁移安全 |
| 存储管理 | 10% | 清理、归档、健康监控 |

### 可行性等级

| 等级 | 说明 |
|------|------|
| A | 高可行，纯代码重构，无新技术风险，1-2 天可完成 |
| B | 中高可行，有成熟方案但需注意边界情况，2-3 天 |
| C | 中可行，引入新技术/依赖，存在兼容性风险，需先验证 |
| D | 低可行，技术风险高或与核心目标关联弱，建议延后 |

### 论证方法

- **正方钢人**：站在需求设计者的立场，构建该需求最强有力的论证——为什么这个需求设计得好，为什么能有效达成目标
- **反方钢人**：站在最严苛评审者的立场，构建该需求最强的反驳——这个设计可能在哪里失效，有什么隐含假设未被验证，有什么替代方案更优
- **综合判定**：正反交锋后，给出权重、可行性、是否保留、如何调整

## 需求逐一论证

### FR-STORAGE-001：存储布局管理

**核心交付**：`StorageLayout` 统一路径管理，消除业务代码硬编码文件名。

#### 正方钢人

这是整个分层存储的**地基**。当前路径常量散落在 `storage.go`、`storage_layout.go`、`diagnostic_service.go` 等至少 5 个文件中，修改存储布局需要同步多处，极易遗漏。`StorageLayout` 集中管理所有路径后：
- 新增层级或修改目录结构只需改一个结构体
- 业务代码通过语义化方法（`ConfigPath()`、`DebugLogPath()`）获取路径，不再关心物理位置
- 为后续数据迁移、平台差异化路径提供统一抽象层
- 可测试性大幅提升：可注入临时目录的 `StorageLayout` 进行单元测试

这是**可维护性目标（30%权重）的核心承载者**，没有它，其他 9 个需求的路径管理都会混乱。

#### 反方钢人

最强反驳有三点：

1. **"消除所有硬编码"是过度工程**。当前代码中 `StorageLayout` 结构体已经存在（`internal/appcore/storage_layout.go`），只是字段不够完善。所谓"硬编码"很多是文件名常量（如 `"cfip-log.txt"`），这些常量本身就是稳定的契约，集中管理的收益有限。测试代码、一次性脚本中的硬编码是合理的，强制 0 硬编码会增加无谓的抽象。

2. **路径方法膨胀风险**。如果每个文件都对应一个方法，`StorageLayout` 会变成有 20+ 方法的上帝对象，违反单一职责。而且路径方法本身没有逻辑，只是 `filepath.Join`，抽象层的价值存疑。

3. **迁移期双路径维护**。`LegacyPath()` 方法意味着新旧路径并存，业务代码需要同时处理两种路径，反而增加了复杂度。如果迁移是一次性的，为什么不直接迁移完再删除旧路径？

#### 权重与可行性

| 维度 | 判定 |
|------|------|
| 目标贡献 | 可维护性 30% 的基础，所有其他需求依赖 |
| 权重 | **高（必须保留）** |
| 可行性 | **A** — 纯代码重构，无新技术风险 |
| 预估工时 | 1 天 |

#### 审核调整

**保留，但调整验收标准**：

1. 将"业务代码中无硬编码文件名"调整为"**业务逻辑层**无硬编码文件名，测试代码和构建脚本允许例外"
2. `StorageLayout` 方法按类别分组（配置类、日志类、任务类），避免上帝对象
3. `LegacyPath()` 仅在迁移过渡期使用，标注 `@Deprecated`，迁移完成后移除
4. 新增 `StorageLayout` 的职责边界文档：只负责路径解析，不负责文件读写、不负责迁移逻辑

### FR-STORAGE-002：SQLite 热层

**核心交付**：任务快照和运行时状态存入 SQLite WAL，替代 JSON 文件存储。

#### 正方钢人

这是**性能目标（35%权重）的核心承载者**。SQLite 官方基准证明，对小 BLOB（<10KB）读写比文件系统快 35%，且节省 20% 磁盘空间。任务快照正是典型的小 BLOB 场景：
- 结构化数据（status、type、config、snapshot），适合关系模型
- 高频更新（探测过程中每阶段完成都更新），SQLite 事务比"读JSON-修改-写JSON"原子性强得多
- 需要按状态筛选（活动任务/已完成任务），SQLite 索引查询比遍历文件系统快几个数量级
- WAL 模式支持 1 写 N 读并发，前端轮询状态不阻塞写入

debounce 50ms 批量提交进一步将写吞吐从 ~10000 TPS 提升到理论上限（单事务写多行）。这是**唯一能从根本上提升热数据读写性能的方案**。

#### 反方钢人

这是 10 个需求中**风险最高、假设最多**的一个，最强反驳有五点：

1. **性能提升假设未验证**。"SQLite 比文件系统快 35%"的基准是针对 10KB 以下 BLOB 的随机读写。但 CFST-GUI 的任务快照包含完整探测配置和结果统计，**实际大小可能达到 50-200KB**（几百个 colo 的结果），已经超出"小 BLOB"范畴。对于大 BLOB，SQLite 的优势消失，甚至因为 BLOB 存储的页对齐开销而更慢。**没有针对 CFST-GUI 实际数据大小的基准测试，性能提升是假设而非事实。**

2. **gomobile 兼容性是致命风险**。`modernc.org/sqlite` 是纯 Go 实现，但它是否能被 gomobile 正确绑定为 AAR？纯 Go SQLite 实现使用了大量 `unsafe` 和内存管理，与 gomobile 的 JNI 边界可能冲突。如果不兼容，备选方案 `mattn/go-sqlite3` 需要 CGO + NDK，大幅增加 Android 构建复杂度。**这个风险在 PRD 中被轻描淡写为"P1 阶段先验证"，但如果验证失败，整个热层方案需要推翻重来。**

3. **debounce 50ms 引入一致性问题**。任务状态变更（开始/完成/失败）"立即写入"，但进度更新走 debounce。前端轮询时可能读到旧的进度数据，需要额外的内存缓存层来保证读一致性。这增加了架构复杂度——SQLite 是持久层，内存缓存是热层，两者同步逻辑容易出 bug。

4. **SQLite 单写者串行限制**。WAL 模式是 1 写 N 读，但写操作仍然串行。如果同时有 200 个 colo 完成阶段并写快照，所有写事务排队。虽然单事务 <1ms，但 200 个排队就是 200ms，用户可能感知到状态更新延迟。**PRD 中"并发 100 goroutine 写无数据丢失"只验证了正确性，没有验证延迟。**

5. **引入 SQLite 的成本被低估**。二进制体积增加 5-10MB（纯 Go 实现），schema 迁移需要版本化管理，数据库损坏需要恢复策略，WAL checkpoint 需要调度。这些在 PRD 中只有一句话带过，但实际维护成本不低。

#### 权重与可行性

| 维度 | 判定 |
|------|------|
| 目标贡献 | 性能 35% 的核心，但性能提升未经验证 |
| 权重 | **中高（条件保留）** |
| 可行性 | **C** — 引入新依赖，gomobile 兼容性风险高 |
| 预估工时 | 3-5 天（含兼容性验证） |

#### 审核调整

**条件保留，必须增加前置验证门禁**：

1. **P1 第一个任务必须是 SQLite 可行性验证**：
   - 用 `modernc.org/sqlite` 写一个最小 demo，通过 gomobile 绑定为 AAR
   - 在 Android 真机上运行 CRUD 操作
   - 测量任务快照（实际大小 50-200KB）的读写延迟，与 JSON 文件对比
   - **如果 AAR 构建失败或性能无提升，整个需求回退到方案 A（纯文件系统热层）**

2. **任务快照大字段拆分**：SQLite 只存元数据（task_id、status、type、created_at、updated_at、进度统计），完整配置和结果列表存文件系统（`warm/task-archive/<task_id>.json`），SQLite 中存文件路径。这样 SQLite 行大小控制在 <2KB，确保小 BLOB 性能优势。

3. **debounce 策略调整**：
   - 状态变更（pending→running→completed/failed）立即写
   - 进度更新走 debounce，但同时更新内存缓存
   - 前端读取优先走内存缓存，不直接查 SQLite
   - 内存缓存与 SQLite 的同步逻辑需要单独设计和测试

4. **增加并发延迟验收标准**：并发 200 goroutine 写快照，p99 写入延迟 <50ms（而非只验证"无数据丢失"）

5. **明确回退方案**：如果 SQLite 验证失败，热层使用 JSON 文件 + 内存缓存 + debounce 刷盘，性能目标调整为任务快照读写 <2ms

### FR-STORAGE-003：日志系统优化

**核心交付**：追加写 + 大小轮转 + 64KiB 写缓冲，替代当前 O_TRUNC 模式。

#### 正方钢人

这是**直接解决用户最痛问题的需求**。当前 `DebugLogger.Configure` 使用 `O_TRUNC`，每次启动探测任务都会清空历史日志——这意味着如果探测失败，用户想查看上一次的日志来排查问题，日志已经没了。这是一个**数据丢失 bug**，不是优化。

追加写从根本上解决这个问题。大小轮转（10MiB）解决日志无限增长。写缓冲（64KiB）将每次 `Event` 调用从 syscall 降为内存拷贝，写入延迟从 ~50μs 降到 <5μs，吞吐从 ~2000 条/秒提升到 ≥10000 条/秒。

这三个改进是**正交且独立**的：追加写解决数据丢失，轮转解决空间管理，缓冲解决性能。每个都有明确的收益，且实现都是成熟的文件系统操作，无新技术风险。

#### 反方钢人

最强反驳有四点：

1. **写缓冲的数据丢失窗口**。64KiB 缓冲 + 5 秒 flush 间隔，意味着应用崩溃时最多丢失 5 秒或 64KiB 的日志。对于调试关键问题（如探测失败的瞬间），这 5 秒的日志可能正是最需要的。PRD 中说"最多丢失 5 秒日志，可接受"，但**这个"可接受"是假设，没有用户调研支撑**。

2. **轮转时的并发处理**。轮转需要：关闭当前文件 → rename 为归档名 → 打开新文件。这个过程中如果有其他 goroutine 调用 `Event()`，需要处理。当前设计是全局 `sync.Mutex`，轮转时持有锁，所有写操作阻塞。但轮转操作本身涉及文件 IO（close+rename+open），可能耗时几毫秒，期间所有日志写阻塞。**高并发下这可能成为延迟尖峰。**

3. **error-log 整合被低估**。当前 error-log 通过独立的 `AppendErrorLog` 函数写入，与 `DebugLogger` 完全无关。PRD 说"错误日志整合进 DebugLogger"，但这需要：修改所有调用 `AppendErrorLog` 的地方、统一轮转配置、确保错误日志不被普通日志的 verbosity 过滤掉。这不是一个小改动，**PRD 中低估了这个整合的工作量和风险**。

4. **移动端空间占用**。桌面端保留 5 份 × 10MiB = 50MiB 日志可能没问题，但 Android 低端设备存储空间紧张，50MiB 日志可能触发系统清理或用户不满。PRD 中没有针对移动端的差异化配置。

#### 权重与可行性

| 维度 | 判定 |
|------|------|
| 目标贡献 | 直接解决日志丢失 bug，性能目标核心，可靠性目标核心 |
| 权重 | **高（必须保留）** |
| 可行性 | **A** — 纯文件操作，成熟方案 |
| 预估工时 | 2 天 |

#### 审核调整

**保留，调整细节**：

1. **flush 间隔从 5 秒改为 2 秒**，并在以下节点强制 flush：任务开始、任务完成/失败、应用退到后台。将崩溃丢失窗口从 5 秒降到 2 秒，且关键节点不丢失。

2. **轮转操作优化**：轮转时不持有全局锁，而是：
   - 获取锁，记录当前 file 引用，将 file 字段替换为新打开的文件
   - 释放锁
   - 异步关闭旧文件、rename、删除过期归档
   这样轮转期间的写操作直接写到新文件，不阻塞。

3. **error-log 整合分两步**：
   - P0：保持 `AppendErrorLog` 独立函数，但共用轮转逻辑（提取 `LogRotator` 组件）
   - P3（后续迭代）：完全整合进 `DebugLogger`，统一接口
   这样 P0 不阻塞核心功能，降低风险。

4. **移动端差异化默认值**：Android 默认轮转大小 5MiB，保留 3 份（最多 15MiB）；桌面端默认 10MiB，保留 5 份。通过 `LogRotationConfig` 可配置。

5. **增加缓冲命中率监控**：记录 `Event()` 调用中缓冲命中 vs 触发 flush 的比例，用于性能调优。

### FR-STORAGE-004：任务归档与清理

**核心交付**：已完成任务从 SQLite 自动归档到文件系统，定期清理过期数据。

#### 正方钢人

这是**存储管理目标（10%权重）的核心承载者**，也是生产级应用的必备功能。没有归档和清理：
- SQLite 热层会无限增长（每个完成的任务都留在热层），查询性能随数据量下降
- 旧任务快照、旧诊断包、旧备份占用空间，用户无法感知
- 应用长期运行后存储膨胀，可能触发 Android 系统清理或用户卸载

自动归档（任务完成 10 秒后移到温层）确保热层只存活动任务，查询性能稳定。定期清理（30 天任务归档、7 天诊断包、10 份备份）确保存储占用有上限。清理操作异步执行，不阻塞用户操作。

#### 反方钢人

最强反驳有四点：

1. **归档的双读路径复杂度**。归档前任务在 SQLite，归档后在文件系统。前端查询"任务列表"时需要同时查 SQLite（活动任务）和文件系统（已归档任务），合并结果。两种存储的查询能力不同：SQLite 可以按状态/时间筛选排序，文件系统只能遍历文件名。**这导致"查看历史任务"功能的实现复杂度大幅增加，且用户体验不一致（活动任务秒开，历史任务需要遍历文件系统）。**

2. **归档原子性问题**。归档流程：从 SQLite 读 → 写文件 → 验证 → 从 SQLite 删除。如果在"写文件成功但删除 SQLite 行之前"崩溃，下次启动会看到重复任务（两边都有）。如果在"读 SQLite 之后但写文件之前"崩溃，且 SQLite 行已被其他逻辑删除，则数据丢失。PRD 中说"验证文件写入成功后删除"，但**验证本身不是原子的，崩溃窗口仍然存在**。

3. **"应用空闲时清理"的定义模糊**。PRD 定义为"探测任务结束后 5 分钟无新任务"，但如果用户持续运行探测（如定时任务每小时跑一次），清理永远不触发。而且"空闲"检测本身需要状态管理，增加复杂度。**清理应该有一个保底触发机制（如应用启动时异步执行一次），而不是只依赖空闲检测。**

4. **默认保留期是否合理**。30 天任务归档、7 天诊断包——这些数字从哪来？用户可能希望永久保留某些任务（如对比不同时期的测速结果）。**强制自动删除可能导致用户数据丢失，应该提供"保留所有"选项，且清理前应有明确的用户告知。**

#### 权重与可行性

| 维度 | 判定 |
|------|------|
| 目标贡献 | 存储管理 10%，但实现复杂度高 |
| 权重 | **中（建议保留但简化）** |
| 可行性 | **B** — 边界情况多，原子性需仔细处理 |
| 预估工时 | 2-3 天 |

#### 审核调整

**保留，但大幅简化归档策略**：

1. **归档不删除 SQLite 行**。改为标记 `archived=true`，查询时默认过滤已归档（`WHERE archived=false`），提供"查看历史任务"入口（`WHERE archived=true`）。这样：
   - 单一数据源（SQLite），不需要双读路径
   - 归档操作只是一次 UPDATE，原子性有保障
   - 温层文件系统只存任务的完整结果大文件（如完整 CSV 结果），SQLite 存元数据和摘要
   - SQLite 膨胀问题通过清理已归档超过 N 天的行来解决

2. **清理保底触发**：除了空闲触发，应用启动时异步执行一次清理（不阻塞启动）。清理策略全部可配置，提供"保留所有"选项。

3. **清理前不告知用户**（自动清理是后台维护操作），但在设置页展示"已清理空间"统计和"立即清理"按钮，让用户有感知和控制权。

4. **任务归档延迟从 10 秒改为 60 秒**，给用户足够时间查看刚完成的任务详情。

### FR-STORAGE-005：Android 日志导出优化

**核心交付**：Go 侧写临时文件，Kotlin 侧流式复制到 SAF，替代 base64 JS Bridge 传递。

#### 正方钢人

这是**直接解决用户需求"APP 可以成功导出日志"的核心**。当前 base64 方案的内存开销是灾难性的：50MB 日志 → 原始 50MB + base64 字符串 67MB + Kotlin 解码 50MB = 约 167MB 内存峰值，在低端 Android 设备上必然 OOM。这就是为什么"APP 可以成功导出日志"是一个待解决的问题——大日志导出会崩溃。

临时文件 + 流式复制方案将内存峰值降到 8KiB（复制缓冲区），性能提升 20 倍以上。且实现简单：Go 侧写文件、返回路径，Kotlin 侧文件流复制，都是标准 IO 操作。

#### 反方钢人

最强反驳有三点：

1. **Go 侧如何获取 Android cacheDir 路径**。当前 gomobile 绑定的 `mobileapi.Service` 只有 `Init`、`SetEventSink`、`Invoke` 三个方法。`Init` 接收的是运行时目录路径（`filesDir`），不是 cacheDir。Go 侧要写临时文件到 cacheDir，需要：
   - 方案 A：`Init` 时额外传入 cacheDir 路径（修改 gomobile 接口，影响所有调用方）
   - 方案 B：Go 侧写临时文件到已有的 filesDir（但 filesDir 是持久存储，不适合临时文件）
   - 方案 C：Kotlin 侧先创建临时文件，将路径传给 Go 侧，Go 侧写入该路径
   
   **PRD 中没有明确这个路径传递机制，这是一个关键的设计缺口。**

2. **临时文件清理**。导出完成后 Kotlin 侧删除临时文件，但如果导出过程中应用崩溃或用户取消，临时文件残留。长期积累可能占用空间。需要：应用启动时清理 `cacheDir/export/` 下的残留文件，但 PRD 中没有提到这个清理逻辑。

3. **桌面端为什么不统一用临时文件方案**。PRD 说"桌面端仍使用 base64 模式"，但桌面端的 Wails bridge 也有内存限制，大日志导出同样可能有性能问题。保持两套逻辑（桌面 base64、Android 临时文件）增加维护成本。**如果临时文件方案更优，应该统一使用，而不是平台差异化。**

#### 权重与可行性

| 维度 | 判定 |
|------|------|
| 目标贡献 | 直接解决"APP 导出日志"需求，性能目标核心 |
| 权重 | **高（必须保留）** |
| 可行性 | **B** — 路径传递机制需明确，其余为标准 IO |
| 预估工时 | 2 天 |

#### 审核调整

**保留，补充关键设计**：

1. **明确路径传递机制**：采用方案 C——Kotlin 侧在调用 `debug.export` 前，先在 `cacheDir/export/` 创建临时文件，将路径通过 payload 的 `temp_file_path` 字段传给 Go 侧。Go 侧检测到该字段时，直接写入该路径，不返回 base64。这样：
   - 不需要修改 gomobile 接口
   - Go 侧不需要知道 Android 目录结构
   - 临时文件的创建和清理都由 Kotlin 侧负责，职责清晰

2. **临时文件清理**：
   - 导出成功后立即删除
   - 导出失败/取消时在 finally 块中删除
   - `MainActivity.onCreate` 时清理 `cacheDir/export/` 下所有文件（防崩溃残留）

3. **桌面端统一方案**：桌面端也改用临时文件方案（写到 `os.TempDir()`），Wails 侧读取文件返回给前端。统一逻辑，降低维护成本。如果 Wails bridge 不支持文件传递，则桌面端保留 base64，但需在 PRD 中明确说明原因。

4. **复制缓冲区从 8KiB 增大到 64KiB**，减少系统调用次数，提升大文件复制速度。

### FR-STORAGE-006：Android 跨应用读取

**核心交付**：FileProvider content URI + 系统分享面板，导出日志可被其他应用读取。

#### 正方钢人

这是**直接解决用户需求"被其他应用读取"的核心**。当前导出到 SAF 目录的文件，用户需要手动打开文件管理器、找到目录、找到文件、选择打开方式——流程繁琐，且很多用户不知道 SAF 目录在哪里。

FileProvider + 系统分享面板是 Android 标准的跨应用文件共享方式：
- `FLAG_GRANT_READ_URI_PERMISSION` 确保接收方有权限，不需要接收方申请存储权限
- content URI 是 Android 标准的文件引用方式，所有支持 `ACTION_SEND`/`ACTION_VIEW` 的应用都能处理
- 系统分享面板用户体验好，用户可以选择邮件、微信、文件管理器等任意应用
- 这是**唯一能让用户"一键分享日志给开发者"的方案**

#### 反方钢人

最强反驳有四点：

1. **"保留副本"的空间浪费和一致性问题**。PRD 说"导出到 SAF 的同时在 filesDir/logs/ 保留一份副本用于 FileProvider 分享"。这意味着：
   - 每个导出的日志占用双倍空间（SAF 一份 + filesDir 一份）
   - 两份副本可能不一致（用户在 SAF 中修改/删除了文件，filesDir 中的还在）
   - filesDir/logs/ 会无限增长（每次导出都留一份副本），需要额外的清理策略
   
   **这个设计是为了让 FileProvider 能访问文件，但代价是空间浪费和一致性风险。有没有更好的方式？**

2. **FileProvider 暴露面过大**。`file_paths.xml` 中配置 `<files-path name="app_logs" path="logs/" />`，这意味着 `filesDir/logs/` 下的**所有文件**都可以通过 FileProvider 访问。虽然日志已经做了敏感信息脱敏，但仍然是一个不必要的暴露面。**应该只暴露需要分享的特定文件，而不是整个目录。**

3. **content URI 权限是临时的**。`FLAG_GRANT_READ_URI_PERMISSION` 授予的是临时权限，接收方应用在处理完 Intent 后权限可能失效。如果用户想"保存日志到另一个应用的存储空间中长期访问"，临时权限不够。**需要明确是"临时分享查看"还是"持久化访问"，如果是后者需要使用持久化 URI 权限。**

4. **`OpenLogFile` 的无阅读器崩溃**。用 `ACTION_VIEW` 打开文本文件，如果用户设备上没有安装任何文本阅读器，`startActivity` 会抛出 `ActivityNotFoundException`，导致应用崩溃。PRD 中没有提到这个异常处理。

#### 权重与可行性

| 维度 | 判定 |
|------|------|
| 目标贡献 | 直接解决"被其他应用读取"需求（15%权重） |
| 权重 | **高（必须保留）** |
| 可行性 | **A** — Android 标准 API，成熟方案 |
| 预估工时 | 1-2 天 |

#### 审核调整

**保留，优化分享机制**：

1. **不保留永久副本**。分享时的流程改为：
   - 用户点击"分享日志"
   - Kotlin 侧从 SAF 导出目录复制最新日志到 `cacheDir/share/<timestamp>.txt`（临时文件）
   - 构建 FileProvider content URI 指向该临时文件
   - 调起系统分享面板
   - 分享完成后（或 1 小时后）清理临时文件
   
   这样：不占用持久存储空间，不需要维护两份副本的一致性，FileProvider 只暴露 `cacheDir/share/` 下的临时文件。

2. **FileProvider 缩小暴露面**。`file_paths.xml` 只配置 `<cache-path name="share_files" path="share/" />`，不暴露整个 logs 目录。

3. **明确分享语义**。本需求实现的是"临时分享查看"（用户通过分享面板发送到其他应用，接收方立即处理）。如果需要"持久化访问"，用户可以选择"保存到文件"应用，将日志保存到自己的存储空间。PRD 中明确这一点，不做持久化 URI 权限。

4. **异常处理**。`OpenLogFile` 和 `ShareFile` 都需要 `try-catch ActivityNotFoundException`，捕获后提示用户"未找到可打开此文件的应用，请安装文本阅读器"。

5. **分享文件类型支持**。除了日志（.txt），还支持诊断包（.zip）、配置（.json）、CSV 结果（.csv），`ShareFile` 方法根据文件扩展名自动设置 MIME 类型。

### FR-STORAGE-007：Android Logcat 采集

**核心交付**：诊断包导出时自动包含 Android 原生层 Logcat 日志。

#### 正方钢人

诊断包的价值在于"一站式收集所有调试信息"。当前诊断包只包含 Go 侧日志，但 Android 原生层（Capacitor plugin、前台服务、WorkManager）的崩溃和异常只存在于 Logcat 中。如果用户遇到原生层崩溃（如前台服务 ANR、FileProvider 配置错误），Go 侧日志中完全没有线索，开发者无法排查。

Logcat 采集是专业诊断工具的标配。实现简单（`Runtime.getRuntime().exec("logcat -d -t 500")`），风险低（5 秒超时保护），收益高（原生层问题可排查）。

#### 反方钢人

   - 5 秒超时可能不够（logcat 在低端设备上可能很慢），但超时又不能太长（否则阻塞诊断包构建）

3. **优先级过低，不应阻塞核心功能**。Logcat 采集是" nice to have"，没有它诊断包仍然有用（Go 侧日志是主要调试信息）。但它需要额外的测试（不同设备/Android 版本的兼容性），可能拖慢整个 PRD 的交付。**应该移到后续迭代，先交付核心存储分层功能。**

### FR-STORAGE-008：配置版本化备份

实现简单：保存前读当前配置 → 写备份文件 → 写新配置 → 删除最旧备份（超过 10 份时）。都是标准文件操作，无技术风险。可恢复功能让用户有"后悔药"，提升用户信任。

### FR-STORAGE-009：存储健康检查增强

**核心交付**：`storage.health` 返回分层用量统计（各层已用字节、文件数、可清理空间）。

#### 正方钢人

存储管理需要可观测性。用户和开发者需要知道：
- 存储占用了多少空间？
- 哪一层占用最多？
- 有多少空间可以通过清理释放？

当前 `storage.health` 只检查根目录是否可写，完全没有用量信息。增强后前端可以展示存储用量条，用户可以直观了解存储状态，决定是否需要清理。这是存储管理功能的基础。

#### 反方钢人

最强反驳有三点：

1. **遍历统计的性能问题**。"每层统计文件数和字节数"需要遍历目录。`cold/exports/` 可能有大量导出文件（用户长期不清理），遍历可能耗时几百毫秒到几秒。PRD 要求健康检查耗时 <100ms，**在文件数多时根本达不到**。而且健康检查可能被前端频繁调用（如设置页轮询），每次都遍历目录会导致性能问题。

2. **"可清理空间估算"的准确性**。要估算可清理空间，需要知道哪些文件过期（超过保留期），这需要读取每个文件的修改时间或元数据。对于大量文件，这进一步增加耗时。而且估算结果可能不准确（如文件正在被写入、元数据不可靠），**给用户一个不准确的数字比不给数字更糟糕。**

3. **前端 UI 不在本 PRD 范围**。健康检查返回了分层用量数据，但前端如何展示（用量条、各层详情、清理按钮）需要前端开发。PRD 中没有包含前端需求，意味着后端做了接口但前端不用，功能不可见。**应该要么包含前端需求，要么移到后续迭代。**

#### 权重与可行性

| 维度 | 判定 |
|------|------|
| 目标贡献 | 存储管理可观测性，非核心路径 |
| 权重 | **低（建议简化或移到后续迭代）** |
| 可行性 | **B** — 遍历性能需优化 |
| 预估工时 | 1 天（后端）+ 1 天（前端） |

#### 审核调整

**保留但大幅简化，前端 UI 移到后续迭代**：

1. **健康检查异步执行 + 缓存**：
   - `storage.health` 调用时立即返回缓存结果
   - 后台异步执行实际统计，更新缓存
   - 缓存有效期 5 分钟，避免频繁遍历
   - 这样接口响应 <10ms，不阻塞前端

2. **简化统计内容**：
   - 只统计各层根目录的总字节数（`os.Stat` 目录大小，或限制遍历深度为 1 层）
   - 不统计文件数（遍历开销大，价值低）
   - "可清理空间"只做基于保留策略的粗略估算（如"任务归档超过 30 天的部分"），不精确计算
   - 不递归遍历子目录

3. **前端 UI 移到 v1.1**：v1.0 只实现后端接口，前端不展示。接口返回的数据可供开发者调试使用。

4. **增加手动刷新机制**：`storage.health?refresh=true` 强制重新统计（忽略缓存），用于用户点击"刷新"按钮时。

### FR-STORAGE-010：数据迁移

**核心交付**：从旧版扁平存储惰性迁移到新版分层存储，无数据丢失。

#### 正方钢人

这是**兼容性的必须项**。现有用户已经有配置、日志、任务快照、导出文件，如果升级后数据丢失，用户会流失。迁移方案必须安全、可靠、可回滚。

惰性迁移是合理的策略：不阻塞启动（不一次性迁移所有数据），按访问触发（用户用到什么才迁移什么），迁移不删除旧文件（可回滚）。这是渐进式升级的最佳实践。

#### 反方钢人

最强反驳有四点：

1. **日志不能惰性迁移**。PRD 说"配置和日志采用惰性迁移（首次访问时）"，但日志是追加写——如果旧日志不迁移，新日志直接写到新位置 `logs/cfip-log.txt`，旧日志留在根目录 `cfip-log.txt`。用户查看日志时只会看到新日志（因为读的是新路径），旧日志永远不会被"访问"到，**等于永久丢失**。日志必须在启动时强制迁移，不能惰性。

2. **"惰性迁移"的实际效果**。惰性迁移意味着：用户升级后先运行探测（写新数据到新位置），旧的配置/任务可能一直不被访问，直到用户主动查看历史。如果用户从来不查看历史任务，旧任务快照就永远留在旧目录，占用空间但不被使用。**这导致存储混乱（新旧数据并存），且用户可能误以为旧数据丢失了（因为新界面不显示旧目录的数据）。**

3. **迁移状态的持久化问题**。迁移状态记录在 `storage.json` 中，但 `storage.json` 本身的位置在新旧版本中是否一致？如果旧版本的 `storage.json` 在根目录，新版本也在根目录，那没问题。但如果新版本改变了 `storage.json` 的位置（如移到 `warm/config/`），迁移状态无法传递。**PRD 中没有明确 `storage.json` 的位置在迁移前后保持一致。**

4. **Android 迁移触发点不明确**。PRD 说"Android 端由 AndroidStorageMigration 在版本升级时执行一次性迁移"，但 Capacitor 应用的"版本升级"触发点是什么？
   - `Application.onCreate`？（每次启动都执行，需要判断版本号）
   - `MainActivity.onCreate`？（同上）
   - 还是通过 `BroadcastReceiver` 监听 `MY_PACKAGE_REPLACED`？（应用更新后触发一次）
   
   **触发点不明确会导致迁移逻辑重复执行或遗漏。**

#### 权重与可行性

| 维度 | 判定 |
|------|------|
| 目标贡献 | 兼容性必须项，数据可靠性核心 |
| 权重 | **高（必须保留）** |
| 可行性 | **B** — 边界情况多，需仔细处理 |
| 预估工时 | 2 天 |

#### 审核调整

**保留，修正关键缺陷**：

1. **日志强制迁移**：应用启动时检测旧路径 `cfip-log.txt` 和 `error-log.txt`，如果存在且新路径不存在，**立即迁移**（move 到 `logs/` 目录）。不能惰性。迁移完成后删除旧文件。

2. **启动时全量扫描 + 后台迁移**：
   - 启动时扫描旧目录，列出所有待迁移数据（配置、任务、日志、导出、备份）
   - 日志立即迁移（阻塞，但很快）
   - 其他数据在后台异步迁移（不阻塞启动）
   - 迁移进度记录到 `storage.json`
   - 这样即使不"惰性访问"，数据也会被迁移，不会永久留在旧目录

3. **明确 `storage.json` 位置不变**：`storage.json` 始终在应用数据根目录，不随分层迁移改变位置。PRD 中明确这一点。

4. **Android 迁移触发点**：使用 `BroadcastReceiver` 监听 `Intent.ACTION_MY_PACKAGE_REPLACED`（应用更新后触发一次），在 receiver 中执行迁移。同时在 `MainActivity.onCreate` 中检查迁移状态，如果未完成则执行（兜底）。

5. **迁移完成后的旧文件清理**：所有数据迁移完成后，旧文件保留 7 天（防回滚），7 天后自动清理。提供 `storage.force_clean_legacy` 命令手动清理。

### 关键风险清单（按严重度排序）

| 风险 | 严重度 | 需求 | 缓解措施 |
|------|--------|------|---------|
| `modernc.org/sqlite` 与 gomobile AAR 不兼容 | **致命** | FR-002 | P1 第一个任务验证，不通过则回退到文件系统热层 |
| 日志惰性迁移导致旧日志丢失 | **高** | FR-010 | 修正为启动时强制迁移日志 |
| 写缓冲崩溃丢失关键日志 | **中** | FR-003 | flush 间隔降为 2 秒，关键节点强制 flush |
| Go 侧无法获取 Android cacheDir 路径 | **中** | FR-005 | Kotlin 侧创建临时文件并传路径给 Go 侧 |
| SQLite 任务快照实际大小超出小 BLOB 范围 | **中** | FR-002 | 大字段拆分到文件系统，SQLite 只存元数据 |
| 归档双读路径复杂度 | **中** | FR-004 | 改为标记归档不删除，单一数据源 |
| FileProvider 暴露面过大 | **低** | FR-006 | 只暴露 cacheDir/share/ 临时文件 |

### 评审结论

**PRD v1.0 整体方向正确，但需要以下关键调整后才能进入开发：**

1. **FR-002 SQLite 热层必须增加前置验证门禁**——这是整个 PRD 中风险最高的需求，验证失败会导致热层方案推翻。必须先做 gomobile AAR 兼容性验证和实际数据大小的性能基准测试，再决定是否全面采用 SQLite。

2. **FR-010 数据迁移的日志迁移策略必须修正**——惰性迁移不适用于日志，会导致旧日志永久丢失。必须改为启动时强制迁移。

3. **FR-005 Android 导出优化必须补充路径传递机制**——Go 侧如何获取临时文件路径是关键设计缺口，PRD 中未明确。建议采用 Kotlin 侧创建临时文件并传路径的方案。

4. **FR-007 和 FR-008 移到 v1.1**——这两个需求与分层存储核心目标关联弱，优先级低，移到后续迭代可以让 v1.0 更聚焦、更快交付。

5. **FR-004 归档策略简化**——"归档后删除 SQLite 行"引入双读路径和原子性问题，改为"标记 archived=true 不删除"更简单可靠。

6. **FR-006 分享机制优化**——"保留永久副本"有空间浪费和一致性风险，改为"分享时复制到临时缓存目录"更合理。

完成以上调整后，PRD 可以进入开发阶段。建议先从 P0 五个需求开始（不依赖 SQLite 验证结果），SQLite 热层（FR-002）并行做验证，验证通过后再全面开发。
