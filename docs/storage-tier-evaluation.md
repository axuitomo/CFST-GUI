## 运行特征假设与结论摘要（2026-08-25 二次评价修订）

> **运行特征假设（修订）**：应用运行于**高并发网络环境**——大量并发网络探测/测速任务，结果与日志事件产生频率高、数据量大；但**存储写入本身是低并发**（写入收敛为单一/低并发通道）。在此约束下：
>
> - **网络主流程不应被存储写入阻塞**：事件/结果写入必须与探测解耦（异步队列 / 批量刷盘），否则高并发探测会被存储 IO 拖垮。
> - **性能关注点从「并发」转向「写入吞吐与解耦」**：原「W4 并发安全」分项价值大幅下降（存储低并发下无并发写竞争），替换为「W4 写入解耦 / 异步批处理」。
> - **数据量大使轮转、保留策略、写放大成本更重要**：方案在磁盘占用、轮转成本上的表现被放大。

> **最新结论摘要（修订）**：主权重调整为 **可维护性 70 : 性能 30**。重跑评分后，**S5「append-only 事件日志 + 增量索引」仍以 88.6 分居首，S1 仍居第二**，结论对权重鲁棒、**最终推荐维持 S5**。排序变化：S4 因异步解耦优势升至第 3（原第 4），S6 降至第 4（原第 3），S3 因双写写放大跌至第 9（原第 7）。详细论证与矩阵见 [§9 依据新约束的二次评价](#9-依据新约束的二次评价2026-08-25-修订)。
>
> 以下 §1-§8 为**第一轮评价（原约束：单端单任务、写入峰值仅探测阶段、量级每秒数百行）**，保留作为对比基线；**最新结论以 §9 为准**。

## 1. 评价框架

### 1.1 权重分配方案与理由

本方案采用「性能」与「可维护性」两个一级维度。**主推荐权重为 可维护性 60 : 性能 40**，理由：

- **项目定位**：CFST-GUI 是桌面（Wails）+ WebUI + Android（Capacitor/gomobile）+ CLI 四端共享的测速工具，单端单任务、非高并发服务端。写入峰值仅在探测阶段（高频 `Debugf` 日志 + 结果 CSV），读取峰值在 `task.list`/`task.results`/`diagnostics.export`，量级为每秒数百行，远未达到需要数据库引擎支撑的压力。
- **长期成本集中在可维护性**：跨四端契约（`cfst-gui-command-v2`）、便携模式整体迁移、日志需被其他应用读取、旧数据兼容回退，这些一旦出错是"结构级"返工；而性能问题多为"参数级"调优（缓冲、轮转阈值）。
- **性能红线已被目标架构覆盖**：只要做到"写入不阻塞探测（批量刷盘）+ 列表/导出不全目录扫描（索引）"，性能即可达标；这两点（见 §6）在推荐方案中直接内建，无需为追求更高吞吐引入存储引擎复杂度。
- 因此性能权重定 40%：给予足够权重防止"为了简单牺牲写入/查询体验"，但不至于让"高吞吐依赖"（如 SQLite/KV）主导决策。

### 1.2 评分维度与标准

每个方案在两个一级维度下分项打分，**每项 1-5 分**：

| 一级维度 | 分项 | 满分 | 说明 |
| --- | --- | --- | --- |
| 性能（P） | W1 写入效率 | 5 | 高频日志/结果写入吞吐、批量刷盘能力 |
| | W2 读取/查询效率 | 5 | 列表、检索、导出读取成本（是否全目录扫描） |
| | W3 IO 量与磁盘占用 | 5 | 写放大、冗余、压缩归档空间收益 |
| | W4 并发安全 | 5 | 多写/读写并发的一致性保障 |
| 可维护性（M） | M1 结构清晰度/简单性 | 5 | 目录/格式人可读程度、概念抽象成本 |
| | M2 迁移与兼容成本 | 5 | 对现有 `StorageLayout`/命令契约/旧数据的影响 |
| | M3 诊断与可观测性 | 5 | 无需专用工具即可查看、定位、审计 |
| | M4 备份与恢复 | 5 | 便携复制、归档还原、一致性备份难度 |
| | M5 跨端适配与依赖风险 | 5 | Windows/macOS/Linux/Android 一致性、新增依赖风险 |

综合分计算：`综合 = (P合计/20×100)×Wp + (M合计/25×100)×Wm`。

## 3. 十个方案详述

### S1 纯文件分桶 + JSONL

**① 定位**：延续 [storage-tier-design.md] 主体设计，目录即分层、JSONL 即格式，零新增依赖。

**② 架构/数据流**：热层为 `Root/*.json`（config/draft/scheduler/source-profiles，`WriteFileAtomic` 0o600）；温层为 `tasks/yyyy/MM/{id}.json|{id}-results.json`、`logs/app/*.jsonl`（0o644）、`exports/yyyy/MM/`；冷层 `backups/`、`archive/`（zip/`.jsonl.gz`）。写入统一走 `storagewriter`（原子写 + 按类型权限），`tasks/index.jsonl` 提供增量索引。

**③ 多平台适配性**：纯 `os`/`path/filepath` 实现，Windows（`%APPDATA%`）、macOS/Linux（`os.UserConfigDir`）、Android 应用目录、便携模式（`portableDataDir()`）全部一致；权限按 §3.3 表逐平台归一（Unix mode / Windows ACL）。

**④ 性能特征**：写入 = 顺序 append + 批量刷盘（256 KiB/1s），无 DB 开销；读取靠目录前缀 + `index.jsonl` 裁剪，避免全目录扫描；gzip 归档降低磁盘占用；单进程锁 + 原子写保证并发一致。

**⑤ 可维护性特征**：结构完全透明，`cat`/`jq` 直接可读；迁移仅目录调整，旧路径回退逻辑简单；备份 = 整目录复制（便携友好）。

**⑥ 适用场景与局限**：适用四端一致、被其他应用读取、便携迁移的 CFST-GUI；局限是索引需自维护（损坏可重建）、无 SQL 级聚合查询。

**可行性依据**：与上轮设计逐条对应；`WriteFileAtomic`/`CSVWriter`/`DebugLogger` 均已有实现基础，只改布局与权限，不动命令契约。

---

### S2 单文件 SQLite 全量入库

**① 定位**：所有配置/任务/结果/日志元数据入 SQLite 单文件，查询能力最强。

**② 架构/数据流**：`Root/cfst.db` 承载 config/tasks/results 表 + 日志表；`WriteFileAtomic` 由事务替代；`task.list`/`task.results` 走 SQL 索引；CSV 仍由 `CSVWriter` 生成（对外导出），诊断 zip 由 DB 导出组装。

**③ 多平台适配性**：SQLite 需驱动——gomobile 默认禁用 cgo，需引入 `modernc.org/sqlite`（纯 Go）或 cgo 变体，Windows/macOS/Linux 均需新依赖；WebUI/CLI 需同一 DB 访问层；便携模式单文件复制需停写或 `.backup` 保证一致性。

**④ 性能特征**：写入事务批量、索引查询极快；但日志高频写入 + WAL + 定期 `VACUUM` 有写放大，DB 文件膨胀需监控；读写并发由 WAL 支撑良好。

**⑤ 可维护性特征**：单文件黑盒，需 `sqlite3` 工具；迁移成本最高（全量改写读写路径 + 契约 `task.results` 流式读取语义重做）；日志需额外导出链路才能被其他应用读取。

**⑥ 适用场景与局限**：适合查询/聚合密集、单机强一致场景；对"便携整体复制 + 被其他应用读 JSONL + 四端零依赖"需求不匹配。

**可行性依据**：技术上 Go/SQLite 可行（`modernc.org/sqlite` 支持 Android），但 `internal/contracttest` 固定流式读取与 32MiB 上限语义，且引入驱动与迁移成本，可行性评级"技术可行、工程代价高"。

---

### S3 SQLite 索引 + 文件正文混合

**① 定位**：SQLite 只存元数据/索引（任务清单、状态、时间），正文（JSONL 日志、CSV 结果）保留文件，兼顾检索与可读。

**② 架构/数据流**：写入时双写——文件正文（同 S1）+ SQLite 索引行；`task.list` 查 DB，`task.results`/`debug.export` 按 DB 索引定位文件读取；冷层归档文件 + DB 索引保留指针。

**③ 多平台适配性**：仍需 SQLite 驱动（同 S2 依赖约束）；双写逻辑需四端一致，便携模式需同时携带 DB 与文件目录。

**④ 性能特征**：查询最强（DB 索引）；但每次写入双份（文件+DB）有写放大；崩溃时文件与索引可能不一致，需重建索引兜底。

**⑤ 可维护性特征**：结构与诊断介于 S1/S2 之间（文件可读、索引需工具）；迁移成本高（引入 DB + 同步逻辑 + 契约调整）；备份需文件+DB 一致性快照。

**⑥ 适用场景与局限**：适合"检索强 + 正文需可读"的混合场景；对 CFST-GUI 而言增加一整套索引同步与一致性成本，收益有限。

**可行性依据**：技术上可行，但与 S1 的 `index.jsonl` 相比，用 SQLite 做索引的增量收益（SQL 查询）在单用户测速工具中价值低，工程代价高。

---

### S4 内存热缓存 + 本地冷存

**① 定位**：高频日志/结果先写内存环形缓冲，批量刷盘到本地文件，读取优先命中内存。

**② 架构/数据流**：`DebugLogger` 增加内存缓冲层（容量可配，如 4096 行），满/定时/终态事件刷盘到 `logs/app/*.jsonl`；任务结果先入内存再落 `exports/`；冷层归档同 S1。

**③ 多平台适配性**：纯内存 + 文件，无平台依赖；Android 低内存设备需调小缓冲；便携模式无额外负担。

**④ 性能特征**：写入峰值完全被缓存吸收，刷盘 IO 极少；热数据读取零 IO；但崩溃丢缓冲内未刷盘日志（可接受，终态强制刷盘兜底）；内存占用随缓冲增大。

**⑤ 可维护性特征**：结构清晰（文件仍是最终真相）；但"内存态不可直接读"削弱诊断即时性；刷盘策略需调参。

**⑥ 适用场景与局限**：适用日志写入极高频、读热数据为主的场景；CFST-GUI 探测日志频率下 S1 的行缓冲已足够，内存缓存属于可选增强而非必选。

**可行性依据**：可在 S1 基础上作为 `DebugLogger` 缓冲策略增量实现，无契约影响；风险仅在崩溃一致性（终态强制 `Flush`+`fsync` 已兜底）。

---

### S5 append-only 事件日志 + 增量索引

**① 定位**：把"日志、任务快照、状态变化"统一抽象为 append-only 事件日志，配单一增量索引加速检索——性能与可维护性双优。

**② 架构/数据流**：所有事件（`probe.*`、`task.*`、`storage.*` 审计）追加到 `logs/app/events.jsonl`（同一热段，`O_APPEND` + 行缓冲批量刷盘）；任务/配置等"当前状态"仍以固定文件承载（热层，`WriteFileAtomic`）；`tasks/index.jsonl` 与事件日志同段追加，作为检索索引；冷层轮转 `.jsonl.gz` + 归档。

**③ 多平台适配性**：纯文件实现，四端与便携模式完全一致；`DebugLogger` 现有 JSONL 序列化直接复用（已是 `json.Marshal` 每行），仅扩展事件类型与索引文件；权限按 §3.3（日志 0o644、状态 0o600）。

**④ 性能特征**：写入 = 纯顺序 append，磁盘友好、吞吐最高（W1 5 分）；检索靠增量索引（W2 4 分），索引损坏可扫描重建；gzip 归档空间收益大（W3 5 分）；单写者 + 锁内轮转保证并发一致（W4 5 分）。

**⑤ 可维护性特征**：JSONL 全可读、索引可重建（诊断 5 分）；迁移仅新增事件类型与索引，旧路径回退逻辑与 S1 相同；备份 = 日志+索引整目录复制（索引可重建兜底，备份恢复 4 分）；零新增依赖（跨端 5 分）。

**⑥ 适用场景与局限**：适用"写入为主、检索为辅、强可观测"的本地工具；局限是需要设计事件 schema 与索引重建逻辑，抽象略高于纯目录方案。

**可行性依据**：直接复用现有 `DebugLogger` JSONL 输出 + 上轮已规划的 `index.jsonl` 与 `O_APPEND`；`storage.health`/`debug.export`/`diagnostics.export` 契约不变（仅增强），`internal/contracttest` 基线稳定。

---

### S6 目录分桶 + gzip 归档驱动

**① 定位**：以"一律压缩归档"为核心的分层驱动，空间效率优先。

**② 架构/数据流**：温层按日分桶（`tasks/yyyy/MM/`、`exports/yyyy/MM/`）；超期温数据经 gzip/zip 压缩进 `archive/`；轮转日志直接 gzip；保留策略即"归档 + 按份数/天数清理"。

**③ 多平台适配性**：纯文件 + 标准 gzip/zip（`archive/zip` 已在用），四端与便携一致。

**④ 性能特征**：压缩省空间（W3 5 分）；但读取需解压（W2 3 分），写入分桶无额外开销（W1 3 分）；压缩时机放后台，避免阻塞探测。

**⑤ 可维护性特征**：结构清晰（W1 4 分）；诊断需解压查看（M3 3 分）；备份恢复为整目录（M4 4 分）。

**⑥ 适用场景与局限**：适用空间敏感、低频读取历史数据的场景；CFST-GUI 作为保留策略的"冷层实现"非常合适，但作为"全量方案"会牺牲即时诊断。

**可行性依据**：gzip/zip 能力已在 `archivecore`/`BuildDiagnosticPackage` 就绪；可作为 S1/S5 的冷层具体实现，而非独立主方案。

---

### S7 嵌入式 KV（bbolt / Badger）

**① 定位**：任务快照与索引入嵌入式 KV，日志仍为文件，替代目录分桶与 `index.jsonl`。

**② 架构/数据流**：`Root/cfst-kv/` 存任务清单/状态/检索索引（key=task_id/时间桶）；正文 JSONL/CSV 仍落文件；`task.list`/`task.results` 走 KV 遍历或范围查询。

**③ 多平台适配性**：bbolt 纯 Go 支持 Windows/macOS/Linux/Android（32 位受限需注意）；Badger 纯 Go 但需 mmap 与文件句柄策略，Android 沙箱需验证；新增依赖进入四端构建链。

**④ 性能特征**：KV 写读快、范围查询可用（W1/W2 4-5 分）；但 DB 文件 + WAL 有写放大，需 compaction（W3 3 分）；并发单写者锁。

**⑤ 可维护性特征**：黑盒，诊断需专用工具导出（M3 2 分）；备份需停写或一致性快照（M4 2 分）；迁移与依赖风险高（M2/M5 2 分）。

**⑥ 适用场景与局限**：适用 key-value 随机访问密集场景；对 CFST-GUI 的任务量（单用户、日数十任务）属于过度工程，且便携整体复制与诊断受影响。

**可行性依据**：技术上 Go 生态成熟，但相对 S1/S5 收益有限、引入依赖与一致性/备份复杂度，可行性评级"可行但性价比低"。

---

### S8 本地 + WebDAV 远程双层

**① 定位**：本地文件为主（热/温），WebDAV 作为冷层异地归档（复用现有 `webdav.backup/restore` 契约）。

**② 架构/数据流**：热/温层同 S1（本地）；冷层除本地 `backups/` 外，定期将归档/压缩包 PUT 到 WebDAV 远端（`archivecore.WebDAVRequest`）；`webdav.restore` 可还原。

**③ 多平台适配性**：本地部分四端一致；WebDAV 依赖网络与远端可达性，Android 后台网络受限需按策略节流；配置走 `cfst-gui-config-v2` 的 `backup.webdav` 分域（已有）。

**④ 性能特征**：本地读写不受影响；远端归档为异步后台 PUT，不与探测竞争；网络失败需重试队列。

**⑤ 可维护性特征**：天然异地备份（M4 5 分）；但本地+远端双份状态管理增加复杂度（M1 3 分）；诊断需区分本地/远端。

**⑥ 适用场景与局限**：适用"防丢备份"诉求；CFST-GUI 已有完整 WebDAV 契约，作为**冷层可选增强**极合适，但不宜作为主分层承载（离线不可用）。

**可行性依据**：`archivecore`/`invokeWebDAVBackup`/`invokeWebDAVRestore` 已实现，仅需扩展归档内容与调度，契约向后兼容。

---

### S9 便携只读共享目录

**① 定位**：便携模式数据目录作为只读共享区，供其他应用/多进程只读消费日志与结果。

**② 架构/数据流**：写侧为本进程（0o644 日志/CSV）；读侧为外部应用按约定路径只读；热/温层同 S1；共享区目录权限与 ACL 由部署方授予。

**③ 多平台适配性**：Windows 共享目录/ACL、Unix 0644/组权限、Android 应用私有目录无法被外部应用直接读（需 SAF 或 content URI 导出）——**跨端差异大**。

**④ 性能特征**：只读共享无写竞争；多进程读并发安全；若允许多写者则需锁（本方案限定只读）。

**⑤ 可维护性特征**：目录清晰可查（M3 4 分）；但权限/ACL 管理、宿主环境差异增加运维成本（M5 2 分）；备份依赖宿主。

**⑥ 适用场景与局限**：适用"固定部署环境、多进程只读消费"；Android 沙箱下不可行，便携模式跨设备依赖宿主配置。

**可行性依据**：权限语义与 `logs` 0o644 目标一致，可作为对外读取的**部署增强说明**（见 storage-tier-design §3.3），不作为主分层方案。

---

### S10 最小改动基线（现状 + 日志修复）

**① 定位**：只修 P1/P2/P3（`O_APPEND` + 轮转 + 0o644），其余存储布局维持现状，作为对照基线。

**② 架构/数据流**：`tasks/` 保持平铺、`exports/` 不分桶、无索引；仅日志文件改 JSONL 追加 + 轮转。

**③ 多平台适配性**：四端与便携模式无新增依赖，迁移面最小。

**④ 性能特征**：P5（平铺扫描）、P8（cfst-results 无清理）未解决，`task.list`/诊断打包随任务量线性变慢（W2 2 分）；写入修复后改善（W1 2 分）。

**⑤ 可维护性特征**：无迁移（M2 5 分）、结构清晰（M1 4 分）；但无索引难查历史、诊断弱（M3 2 分）；P4/P6/P7/P10 均未解决。

**⑥ 适用场景与局限**：仅作"不改架构"的下限对照，验证推荐方案的增量收益。

**可行性依据**：改动最小、风险最低，但无法满足"数据量大、导出高效、目录可维护"的全局目标。

## 6. 最终推荐方案

### 6.1 推荐结论

**推荐采用 S5「append-only 事件日志 + 增量索引」作为最终方案**，落地形态为：**以 storage-tier-design.md 的目录契约（S1）为骨架，将日志/事件写入统一为 append-only JSONL 热段，并配单一 `index.jsonl` 增量索引**。即：**选 S5、沿用 S1 目录、吸收 S4 的行缓冲刷盘、复用 S6 的 gzip 冷层、叠加 S8 的 WebDAV 可选冷备份**。

关键理由（对应评分明细）：

- **性能（P 标化 95，全场最高）**：纯顺序 append 写入对磁盘最友好，直接解决 P9（逐行同步写）与 P2（无轮转）；增量索引解决 P5（全目录扫描）；gzip 冷层解决 P8（无清理）。
- **可维护性（M 标化 88，与 S1 并列最高）**：JSONL 全可读、索引可重建、零新增依赖、便携整体复制、四端契约不变，对应解决 P1/P3/P4/P6/P7/P10。
- **与其他方案相比**：优于 S1 之处在统一事件抽象与检索；优于 S4 之处在不引入内存一致性风险；优于 S6 之处在即时诊断；优于 S2/S3/S7 之处在零依赖、可移植、可读；优于 S8/S9 之处在离线可用、跨端一致。

### 6.2 与 storage-tier-design.md 的衔接（需修订/增强章节）

| 上轮章节 | 衔接动作 | 说明 |
| --- | --- | --- |

| §2.3 能力分层 | **修订** | 写入接口层新增 `EventSink`（append-only 写入器）与 `IndexWriter`（同段索引追加）；日志写入统一经 `DebugLogger` 事件通道 |

## 8. 结论

1. 探索并评价了 **10 个**多平台存储分层方案（文件系 / DB 系 / KV 系 / 缓存系 / 网络系 / 基线对照），每个方案均给出定位、架构、多平台适配、性能、可维护性、适用场景与可行性依据。
2. 采用「可维护性 60 : 性能 40」主权重评分，**S5 append-only 事件日志 + 增量索引以 90.8 分居首**；经可维护性优先 / 均衡 / 性能优先三种权重场景敏感性分析，S5 与 S1 排序稳定，结论对权重不敏感。
3. **最终推荐 S5**，落地形态 = S5 索引机制 + S1 目录契约 + S4 行缓冲 + S6 gzip 冷层 + S8 可选 WebDAV 冷备份，与 [storage-tier-design.md](./storage-tier-design.md) 的 P0-P4 计划无缝衔接，需增强 §2.2/§2.3/§3.2/§5 四个章节。
4. 该方案满足全局目标全部诉求：日志可被其他应用读取（JSONL + 0o644 + 统一目录）、数据量大下可维护（轮转/保留/索引）、跨四端一致（零新增依赖、契约不变）、性能达标（顺序写 + 索引查询）。

## 9. 依据新约束的二次评价（2026-08-25 修订）

> 本节基于用户补充的关键运行特征约束，对 §1-§8 的第一轮评价进行权重修正与评分重跑。**原评价（§1-§8）保留作为基线对照，本节结论为最新有效结论。**

### 9.1 新约束与运行特征假设

用户补充的运行特征约束：

| 维度 | 原假设（第一轮） | 新约束（修订） | 对评价的影响 |
| --- | --- | --- | --- |
| 网络并发 | 单端单任务、非高并发服务端 | **高并发网络环境**：大量并发网络探测/测速任务 | 事件/结果产生频率高、数据量大；网络主流程不得被存储写入阻塞 |
| 存储并发 | 未显式区分 | **存储写入本身低并发**（写入收敛为单一/低并发通道） | 各方案「并发能力」分项价值大幅下降；无需为并发一致性引入 DB/KV |
| 数据量 | 写入峰值每秒数百行 | **结果与日志事件数据量大** | 写入吞吐、批处理、轮转、保留策略、写放大成本成为性能关键 |

由此得到两个直接影响评价的推论：

1. **写入必须与探测解耦（异步）**：高并发网络下，若存储写入同步阻塞在探测主流程内（逐行写、同步 rename），会拖慢探测循环甚至造成事件堆积丢失。因此"写入是否具备异步队列 / 批量刷盘 / IO 解耦能力"成为最重要的性能分项。
2. **性能关注点从「并发」转向「写入吞吐与解耦」**：存储低并发意味着多写/读写并发的竞争不存在，原「W4 并发安全」（SQLite WAL、KV 单写者锁等）几乎没有区分度；应替换为「W4 写入解耦 / 异步批处理」。

### 9.2 权重重新论证：可维护性 70 : 性能 30

**新主权重：可维护性 70 : 性能 30**。理由：

- **存储低并发 → 并发能力分项失去价值**：S2/S3/S7（DB/KV 系）的核心卖点之一是"并发一致性与事务"，在新约束下这些能力不会被用到（写入本就是低并发单写者）；其引入的写放大、黑盒、迁移成本反而在数据量大时成为负担。若维持性能权重 40%，会让 DB/KV 系获得虚高的性能分。
- **网络高并发 → 性能目标收敛为"解耦与吞吐"**：这两点（异步队列 + 顺序 append + 批量刷盘）在文件系方案（S1/S4/S5）中靠轻量机制即可达成，**不需要**引入存储引擎；性能不再是区分主方案的维度，而是"达标的必要条件"。既然达标成本低，权重应下调。
- **长期成本集中在可维护性（不变且加强）**：跨四端契约、便携迁移、日志被外部读取、旧数据兼容回退、海量数据下的诊断与保留——在数据量大后这些"结构级"成本只增不减。
- **定值 30 的合理性**：保留 30% 性能权重，足以否决"为了简单而牺牲吞吐/解耦"的方案（如 S10 无批处理、S6 解压读取），又不至于让 SQLite/KV 的高吞吐幻觉主导决策。性能 30/可维护 70 与敏感性分析中 60/40、50/50 场景结论一致（见 §9.5），对权重选择鲁棒。

### 9.6 最终推荐（修订）

**最终推荐维持 S5「append-only 事件日志 + 增量索引」，落地形态在 §6.1 基础上增强「网络高并发下存储写入解耦/异步批处理」**：

- **主体不变**：append-only 事件热段（`logs/app/events.jsonl`，`O_APPEND` + 行缓冲）+ 单一增量索引 `tasks/index.jsonl` + gzip 轮转冷层 + S1 目录契约。
- **新增增强（回应新约束）**：
  1. **异步事件队列**：在 `EventSink` 与刷盘之间插入有界异步队列（单写者 goroutine + 有界 channel，如 4096 条），探测主流程**仅入队、不等待刷盘**，彻底解除存储 IO 对网络主流程的阻塞。
  2. **批量刷盘保持**：消费侧按 256 KiB / 1s 批量刷盘；关键终态事件（`probe.complete`/`probe.failed`）**同步确认**（Flush+fsync）防丢。
  3. **解耦即低并发**：队列单消费者即保证"存储写入低并发"，天然消除并发写竞争，无需 DB/KV 事务。
  4. **轮转在消费侧**：轮转、gzip、保留策略全部在消费侧（后台）执行，不占探测关键路径。
- **吸收 S4 的内存缓冲思想但改为有界队列**：避免无限内存缓存的内存/崩溃风险，同时保留"写入不被阻塞"的解耦收益。
- **S6 作为冷层实现、S8 作为可选异地冷备份**维持不变。
